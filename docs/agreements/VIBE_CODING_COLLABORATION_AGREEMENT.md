# dreAmIng 바이브 코딩 협업 개발 운영안 — 합의본

> **Status: REFERENCE**
>
> 이 문서는 초기 협업 운영 합의의 보존본입니다. 현재 사람과 LLM의 실행 규칙은 [AGENTS.md](../../AGENTS.md)를 우선합니다.

- 상태: `DECIDED`
- 적용 대상: dreAmIng 스마트농업 서비스 개발팀
- 목적: 서로 다른 LLM과 개발 도구를 사용하더라도 하나의 제품 계약과 검증 기준으로 개발한다.

## 1. 핵심 원칙

> 각자 코딩하기 전에 제품 구조와 연결 규칙을 먼저 합의한다.

바이브 코딩 협업의 목표는 코드를 많이 생성하는 것이 아니라, 서로 다른 사람이 서로 다른 LLM을 사용해도 동일한 제품·데이터·API·테스트 기준을 따르게 만드는 것입니다.

## 2. 왜 이 운영체계가 필요한가

각자 독립적으로 LLM을 사용하면 다음 문제가 발생할 수 있습니다.

- 폴더 구조와 라이브러리가 달라진다.
- 같은 데이터를 다른 이름과 형식으로 정의한다.
- 화면·서버·데이터·AI가 서로 다른 제품을 가정한다.
- 코드는 합쳐져도 실제 사용자 흐름이 연결되지 않는다.
- 요청하지 않은 기능이나 대규모 리팩터링이 추가된다.
- 테스트를 통과했어도 농업적 의미가 틀릴 수 있다.

따라서 GitHub는 코드 저장소뿐 아니라 제품 계약, 작업 범위, 검증 근거를 관리하는 기술 원본으로 사용합니다.

## 3. 팀 공통 개발 원칙

1. 공통 문서를 먼저 만들고 코드는 문서를 따릅니다.
2. 역할이 아니라 작은 사용자 행동 단위로 작업합니다.
3. 한 작업은 하나의 Issue·Branch·Pull Request로 끝냅니다.
4. LLM 결과는 자동 테스트와 사람의 리뷰를 통과해야 합니다.
5. 첫 수직 기능을 완성한 후 병렬 개발을 확대합니다.
6. 공식정보·농장정보·서비스 분석 결과를 구분합니다.
7. 농업 판단은 기술 구현과 별도로 도메인 검토를 받습니다.

## 4. 협업 도구의 경계

### Notion

- 프로젝트 목표
- 회의 내용
- 일정
- 의사결정 요약
- 대외 협업 기록

### GitHub

- 코드
- 기술 문서
- Issue와 Task
- Branch와 Pull Request
- 테스트와 CI
- Architecture Decision Record

같은 기술 문서를 Notion과 GitHub에서 동시에 수정하지 않습니다. Notion에는 GitHub 원본 링크와 결정 요약만 남깁니다.

## 5. 개발 시작 순서

1. MVP 포함·제외 범위를 확정합니다.
2. 제품·도메인·아키텍처·데이터·API 계약을 작성합니다.
3. `AGENTS.md`, Task, Issue, PR 템플릿을 만듭니다.
4. 로컬 실행·테스트·CI가 가능한 프로젝트 골격을 만듭니다.
5. 첫 수직 기능을 한 흐름으로 구현합니다.
6. 수직 기능이 연결된 후 작은 Task로 병렬 개발합니다.
7. 모든 변경은 PR과 자동 테스트를 거쳐 `main`에 합칩니다.

## 6. 첫 번째 공동 개발 범위

```text
농장 등록
→ 작기 등록
→ 규칙 기반 오늘의 작업 생성
→ 오늘 화면에서 작업 확인
→ 완료 또는 문제 기록
→ 사진·메모 저장
→ 작업 이력 조회
→ 문제 발생 시 후속 작업 생성
```

첫 목표는 많은 기능이 아니라 화면·서버·DB·도메인 규칙·테스트·배포가 실제로 연결되는 것을 증명하는 것입니다.

## 7. 역할과 책임

### 팀 리더·PM

- 사용자와 제품 범위 결정
- 우선순위와 완료 조건 결정
- 범위 변경 최종 승인

### 기술 통합 주 책임자

- 저장소와 모듈 구조
- 기술 스택
- DB·API·공통 계약
- 고위험 PR과 merge

### 기술 통합 백업 책임자

- 주 책임자 부재 시 기술 결정 지원
- 통합 구조와 릴리스 지식 공유

### 기능 담당자

- 승인된 Task 범위 안에서 구현
- 테스트와 검증 근거 제출
- 계약 변경 여부 보고

### 데이터·AI 담당자

- 데이터 수집·정규화 구조
- 모델·AI 입력과 출력 계약
- 불확실성과 안전 상태 표시

### 농업 도메인 검토자

- 설향 생육단계와 농작업 용어
- 작업 템플릿과 위험 표현
- 병해충·농약·고위험 판단 검토

## 8. 표준 Task 단위

모든 작업은 다음 항목을 포함합니다.

- 작업 목적
- 현재 맥락과 관련 문서
- 구현 범위와 제외 범위
- 수정 가능 파일과 제한 파일
- 입력과 출력
- 완료 조건
- 필수 테스트
- 보안·농업 안전 조건
- Handoff

“이 기능을 알아서 완성해 줘”와 같은 포괄적 요청은 사용하지 않습니다.

## 9. GitHub 운영 규칙

- 저장소 최초 초기화 이후 `main` 직접 push 금지
- 역할별 장기 브랜치 금지
- 한 PR에는 하나의 행동 변화만 포함
- DB·API·공통 타입 변경은 사전 합의
- 요청하지 않은 리팩터링 금지
- 테스트 삭제·약화 금지
- PR에 변경 목적·검증 결과·남은 위험 기록
- CI와 담당자 리뷰 통과 후 merge

## 10. 합의된 선택

| 항목 | 결정 |
|---|---|
| 기술 통합 책임자 | 주 책임자 1명 + 백업 1명 |
| 기술 스택 | Next.js·TypeScript·Supabase·Vercel |
| 저장소 구조 | Monorepo |
| 데이터 모델 승인 | 기술 통합 책임자 + 농업 도메인 검토자 |
| 일반 PR | 1명 승인 |
| 고위험 PR | 기술 통합 책임자를 포함한 2명 승인 |
| Merge | Squash and merge |
| 완료 기준 | 실제 연결·필수 테스트·CI·테스트 배포·실행 문서 |
| Notion·GitHub | Notion은 운영 요약, GitHub는 기술 원본 |

## 11. 수직 기능 완료 정의

- 농장과 작기 정보를 저장할 수 있다.
- 오늘의 작업이 생성되고 화면에 표시된다.
- 완료 또는 문제 결과가 저장된다.
- 사진 또는 짧은 메모가 저장된다.
- 작업 이력에서 결과를 조회할 수 있다.
- 문제 발생 시 후속 작업을 만들 수 있다.
- lint, typecheck, test, build, CI가 통과한다.
- 다른 팀원이 문서만 보고 실행을 재현할 수 있다.
